Slack's MCP server vs the CLI: what an agent spends

We gave Claude Code the same seven Slack tasks through Slack's hosted MCP server and through this CLI, 35 runs each. With the changes described below, the CLI answered every task correctly at a third less cost per task.

33% lower

mean cost per task: $0.033 with the CLI, $0.050 with MCP

60% less

tool output read by the model: 4,144 vs 10,466 characters per task

35 / 35

tasks answered correctly by each arm in the final run

Final run, 7 tasks × 5 repeats per arm, Claude Sonnet 5 in Claude Code. Costs are the total_cost_usd Claude Code reports for each session.

This is our own benchmark of our own tool, on one workspace. The harness is in the repository so you can run it against yours; the caveats say where the numbers are weak.

What was compared

MCP arm

Slack's hosted MCP server at mcp.slack.com, connected with the OAuth client from Slack's own Claude Code plugin. Its read and search tools are available; its write tools are denied.

CLI arm

The slack CLI and the skill that slack skills add installs. The agent runs it from a shell. Commands that write to Slack are denied.

Method

  • Each run is a fresh, headless Claude Code session (claude -p) on Claude Sonnet 5, with the task as its only prompt. Both arms get the same prompt, word for word. Prompts name the workspace and the facts to find, never a tool.
  • Each arm sees exactly one Slack surface. Sessions load no user plugins or other MCP servers and start in an empty directory outside any repository. The harness reads each session's startup event and stops if an arm sees the other arm's tools or skill.
  • Both arms run with permission prompts bypassed, as a trusted interactive session would, and the same deny rules block anything that writes to Slack. The tasks ran against a real workspace, so writes were never allowed. We checked that deny rules still hold in that mode for plain, compound, looped, piped, and absolute-path commands.
  • There are seven read-only tasks plus a baseline that only replies "OK", which measures fixed overhead. Every question is pinned to past timestamps, so the right answer cannot drift between runs.
  • A run passes when every expected fact appears in the final answer (a set of case-insensitive regular expressions per task). A run that errors or runs out of budget fails.
  • Each task ran 5 times per arm. The arms alternate which goes first on each repeat, so neither always runs with a warmer cache.

The seven tasks

The workspace is a private company workspace, so the page describes tasks by shape and publishes only aggregate numbers.

  1. Search for a status update by keyword and date, and extract three facts from it.
  2. Find a support report and say how its thread was resolved.
  3. Find the person with a given job title and give their name and user id.
  4. Given a message link, name the alert the message shows.
  5. Find a thread by author and date, then follow a reply's link into another channel.
  6. Read a bot's deployment notice at a given minute and report three fields.
  7. List what a person reported in a channel around a given time.

Results

We ran the benchmark three times on the same tasks. Only the CLI arm changed between runs: after each run we read the transcripts, changed the CLI or its skill where the CLI arm spent tokens, and ran again. The MCP arm is the same configuration in all three runs.

The CLI costs less on six of seven tasks. MCP costs less reading the bot's deployment notice: the notice keeps some fields only in its attachment, and the CLI skill tells the agent to read such a message unfiltered. MCP also needs fewer turns on most tasks, because the CLI arm spends one turn loading its skill.

Where the tokens went, and what changed

Most of an agent's Slack cost is what it reads back from tools. In run 1 the CLI arm read about 369,000 characters of tool output across its 35 runs. Almost none of it was the answer:

Share of CLI tool output Run 1 Run 2 Run 3
Listing stored workspaces 37% 11% 1%
Search results 18% 71% 69%
Reading the skill's reference files 15% 0% 0%
Channel history and threads 18% 17% 29%
Total characters, all 35 runs 369,347 371,099 145,051

Each change targeted something the transcripts showed:

  • Dates as dates. Slack's time-range arguments take Unix seconds, so the agent shelled out to date. 13 of the CLI arm's 15 failed tool calls in run 1 were date invocations with the wrong platform's flags. The time-range flags now accept ISO 8601 (--oldest 2026-09-24T21:00), read as UTC.
  • No setup detour. The skill sent the agent to list its workspaces before every task and to read a reference file for the most common reads. Common reads are now in the skill itself, and it lists workspaces only when the workspace is in doubt.
  • Fewer fields. Run 2 showed search results had become most of the output, mostly repeated channel metadata, and the agent trimmed them with a token limit that can cut off the match it needs. The skill now gives ready-made --filter-output field lists for search, history, and threads. In run 3, 53 of the CLI arm's 68 read commands used one, and none used a token limit.
  • Compact JSON. --json printed indented JSON. It now prints one line when the output goes to a program instead of a terminal.
  • Links as arguments. Commands that take a channel and a message timestamp accept a message link instead, so the agent no longer parses links by hand. slack workspaces list also leaves out the token's scopes unless asked with --scopes; they were most of its output.

The first two changes shipped together (run 2) and the last three together (run 3), so the runs measure each group, not each change. They are in CLI 0.4.0 and its framework, incur 0.9.0.

MCP's cost is also mostly tool output: its two search tools produced 84% of its output in the final run. Its tools return formatted text that the agent cannot trim to the fields it needs. In exchange, MCP messages name their authors, where the CLI returns Slack's user ids and the agent looks up a name when it needs one.

Caveats

  • One workspace, one model. All runs used one small company workspace and Claude Sonnet 5. Larger workspaces return more search matches and longer histories, which could move the numbers either way.
  • Small samples, real noise. Each cell is 5 runs. The MCP arm did not change between runs, yet its median cost on the support-thread task moved from $0.127 in run 1 to $0.064 in run 2; in run 3 its five runs ranged from $0.025 to $0.141, depending on how large a search result the model pulled in. Read per-task differences under about 30% as noise. The pooled means are steadier: MCP's mean cost per task was $0.049, $0.049, and $0.050 across the three runs.
  • We tuned against these tasks. The CLI changes came from reading these transcripts, and the same tasks measured them. The changes are general (dates, field filters, compact output, links), but a fresh task set would be a fairer test.
  • MCP needs fewer turns. 4.5 against 5.1 on average in the final run. The CLI arm's extra turn is loading its skill; that cost is included in every CLI number above.
  • One MCP correctness miss. In run 2, one person-lookup run answered with a display name instead of the full name the task asked for; its user search result did not include the full name. The CLI arm passed all 105 runs across the three fair runs.
  • Denied tools disappear. Claude Code removes denied tools from the session, so the MCP arm does not carry the schemas of Slack's 13 write tools. This favors MCP slightly.
  • Our first harness was unfair. It approved commands one prefix at a time, which let MCP tool calls through but blocked the shell helpers an agent uses with a CLI: 30 denied commands in the CLI arm against 1 in the MCP arm. It also ran sessions inside this repository, whose git context advertised the CLI. We discarded that run and fixed both before the three runs above.

Run it on your workspace

The harness is evals/ab in the repository. Authorize the MCP arm once, sign in with the CLI, and write a task file with prompts and the facts each answer must contain: 

# Once: authenticate the MCP arm with /mcp inside this session
$ claude --strict-mcp-config --mcp-config evals/ab/slack-mcp.json
$ slack login
$ node evals/ab/run.ts --tasks evals/ab/tasks/mine.local.json --repeats 5
$ node evals/ab/report.ts evals/ab/results/<run>/runs.jsonl

Files named *.local.json and all results are ignored by git, because tasks and transcripts contain your workspace's messages. The report prints medians per task and arm and counts denied commands and calls to the other arm's tools, so a skewed run is visible.
